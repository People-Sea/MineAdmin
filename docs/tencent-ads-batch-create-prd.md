# 风起（批量广告投放系统）PRD（腾讯广告 MVP 版）

## 1. 背景
当前项目“风起（批量广告投放系统）”准备接入腾讯广告，为多个客户提供批量创建广告的能力。

该场景与普通后台系统不同，主要有 4 个现实约束：

- 系统服务多个客户，必须具备多租户隔离能力。
- 租户授权广告主账号时，必须使用平台分配的腾讯广告第三方应用，不再由租户自行配置应用。
- 广告执行不能长期依赖固定凭证，必须由员工扫码获取临时执行凭证。
- 广告创建、更新、重试都是长链路操作，必须走异步任务。

从业务风险上看，如果某个员工的执行凭证异常或被封，不能影响其他员工、其他项目、其他租户。

因此，本产品的 MVP 目标不是做一个“大而全”的多租户平台，而是先做出一套最小可跑通的闭环：

- 平台能管理多个租户
- 租户能管理员工与项目
- 项目能管理广告主账户、素材与任务
- 员工能扫码获取执行凭证
- 系统能异步执行批量建广告任务

## 2. 解决方案（技术选型）
### 2.1 后端框架
- 使用现有 `MineAdmin` 作为后台基础框架。
- `MineAdmin` 底层依赖 `Hyperf`，继续承担平台后台能力，不再引入官方多租户插件。

### 2.2 数据存储
- 使用 `MySQL` 存储租户、项目、员工、任务、日志等业务数据。
- 使用 `Redis` 承担缓存、队列、临时状态存储。

### 2.3 异步任务
- 使用 `hyperf/async-queue` 作为广告创建、更新、重试的主执行链路。
- 使用 `hyperf/crontab` 做超时巡检、补偿、通知补发，不承担主执行流程。

### 2.4 腾讯广告接入
- 使用腾讯广告官方 API / OAuth 能力对接应用授权、账户授权和广告接口调用。
- 本文中的 `userToken` 先作为业务命名，表示“员工扫码后获得的执行凭证”。
- 当前扫码回调的核心结果是 `userToken`、过期时间，以及可能返回的微信昵称；当前按 15 天有效期理解。
- 当前阶段，腾讯扫码回调只用于给本地员工获取执行凭证，不承担本地账号识别和权限判断。
- 后续开发时，需要在接口对接阶段进一步确认 `userToken` 与腾讯官方 OAuth 字段的对应关系。
- MVP 当前只做腾讯广告，不额外抽象多媒体统一层。
- 产品层直接围绕“广告主账户”做授权和投放，不单独暴露“管家账号 / 授权主体”菜单。
- 技术层保留一层“授权来源记录”，用于保存 OAuth 授权身份、token 刷新和账号同步来源。
- 腾讯广告第三方应用由平台统一管理，并分配给租户使用；租户在授权广告主账号时，必须使用平台已分配应用。

### 2.5 安全策略
- 应用密钥、执行凭证加密存储。
- 队列消息体只传业务 ID，不传明文敏感凭证。
- 所有任务执行链路必须可审计、可追踪。

## 3. 框架架构
MVP 阶段采用“平台域 + 租户业务域 + 腾讯接入域 + 异步任务域”四层结构。

### 3.1 总体结构
```text
+----------------------+
| 平台后台基础框架      |
| MineAdmin            |
| 租户开通/审计/告警    |
+----------+-----------+
           |
           v
+----------------------+
| 租户业务域            |
| 租户/项目/员工/权限链 |
| 模板/素材/任务        |
+----------+-----------+
           |
           +------------------+
           |                  |
           v                  v
+------------------+   +--------------------+
| 腾讯广告接入域    |   | 异步任务域          |
| 广告主账号接入/授权 | | async-queue/crontab|
+------------------+   +--------------------+
```

### 3.2 平台域
平台域继续使用现有 `MineAdmin` 账号体系，只服务“风起（批量广告投放系统）”的平台运营人员。

平台域只负责：

- 租户开通、停用
- 平台应用管理与分配
- 平台级审计
- 全局异常排查
- 平台告警

平台域与租户域共用同一套 `MineAdmin user / role / menu` 体系。
MVP 阶段不再单独建设 `tenant_member` 认证链，而是在统一 `user` 模型上补充 `tenant_id`、`last_project_id` 等字段，再用项目成员关系与账号授权关系完成数据隔离。

### 3.3 租户业务域
租户业务域负责：

- 租户
- 项目
- 租户员工与项目成员关系
- 项目权限
- 广告主账户授权来源记录
- 广告主账户
- 广告主账户授权
- 凭证获取会话与执行凭证
- 广告素材、模板、任务与任务日志

### 3.4 腾讯接入域
负责：

- 平台分配应用校验
- 广告主账户授权回收
- 广告接口调用
- 凭证刷新与异常识别

### 3.5 异步任务域
负责：

- 主任务/子任务拆分
- 执行状态流转
- 失败重试
- 补偿与通知

## 4. 产品组织架构
MVP 阶段，产品组织架构尽量简单，只保留 4 层：

- 平台
- 租户
- 项目
- 员工

其中，腾讯广告第三方应用由平台统一管理并分配给租户使用；租户侧不单独做 `应用管理` 菜单，也不单独暴露“授权主体 / 管家账号”菜单，而是在 `投放账号管理 -> 广告主账号` 中直接完成授权与选择；“广告主账号”“模板”“素材”“任务”都围绕项目展开。租户是管理边界，项目是用户日常操作的主工作上下文。

### 4.1 组织关系图
```text
平台
├── 应用
└── 租户
    ├── 主项目（默认生成）
    ├── 项目 A
    │   ├── 广告主账号
    │   ├── 模板
    │   ├── 素材
    │   └── 任务
    ├── 项目 B
    └── 员工
        ├── 租户管理员
        └── 优化师
```

### 4.2 项目是主工作上下文
在“风起（批量广告投放系统）”里，项目不是一个普通字段，也不是一个附属筛选项，而是租户侧业务操作的主视角。

员工登录后，除少数租户管理页外，默认都应在某个项目上下文中工作。

也就是说，项目切换后，以下内容都应随之切换：

- 广告主账号
- 素材
- 模板
- 任务
- 报表
- 账号授权结果

MVP 阶段建议产品交互遵循以下原则：

- 平台用户与租户用户统一使用 `/login`
- 不再保留 `/tenant/login` 兼容入口，统一收敛到 `/login`
- 平台用户与租户用户共用同一套 `username + password` 登录凭证模型
- 租户用户通过 `user.tenant_id` 识别所属租户，不再额外引入邮箱登录链
- 员工登录后，优先进入自己最近使用或默认可进入的项目
- 页面顶部提供全局“当前项目”切换能力
- 租户管理员可切换本租户全部项目，优化师只能切换自己已加入的项目
- 除租户管理页外，业务页面默认基于当前项目展示数据

### 4.3 MVP 后台菜单结构
MVP 阶段，租户后台建议直接对齐竞品的使用习惯，围绕“配置管理 + 业务模块”来组织，而不是暴露过多技术概念。

建议一级菜单如下：

- 工作台
- 配置管理
- 素材中心
- 模板中心
- 任务中心
- 报表与日志

其中，`配置管理` 下的核心模块建议如下：

- 团队人员管理
- 团队项目管理
- 投放账号管理
  - 广告主账号

这里有两个产品原则：

- 腾讯第三方应用由平台统一管理并分配给租户；租户侧不单独挂 `应用管理` 菜单，授权时直接使用已分配应用
- 租户侧不单独暴露“管家账号 / 授权主体”概念；用户在 `广告主账号` 中直接发起授权、选择并导入广告主账号
- `团队项目管理` 只负责项目与成员配置；广告主账号的授权、导入和归属在 `投放账号管理` 中完成
- `投放账号管理` 是项目工作流里的资源管理入口，`广告主账号` 是真实投放对象，也是当前 MVP 唯一需要暴露的投放账号模型

### 4.4 产品口径与技术口径
为了贴近用户理解，产品页面建议直接使用竞品同类口径：

- 产品页叫 `广告主账号`
- 产品页叫 `团队项目管理`
- 产品页叫 `团队人员管理`
- 产品页叫 `投放账号管理`

在技术实现中，也保持简单直接：

- `广告主账号` 对应内部的“广告主账户”
- 应用配置由平台管理；租户侧只感知“当前已分配可用应用”，不直接维护应用密钥
- 租户侧页面不单独出现“授权主体”菜单，但系统内部保留 OAuth 授权来源记录

这样做的目的，是让前台交互和底层模型尽量一致，避免为了未来不确定场景过早引入中间层。

### 4.5 为什么 MVP 要保留“项目”
项目是本产品最快落地、同时最方便扩展的中间层。

不加项目会带来两个问题：

- 广告主账户、模板、素材、任务都会直接堆在租户下，后续难管理。
- 员工的数据权限只能在“全租户”级别做控制，粒度过粗。

MVP 先引入项目，可以同时解决：

- 广告主账号分组管理
- 员工按项目协作
- 任务归属清晰
- 后续报表按项目聚合更自然

### 4.6 MVP 角色模型
MVP 只保留最少角色，不做复杂角色树。

- 角色能力直接复用 `MineAdmin` 角色与菜单权限体系，不再维护一套平行角色枚举
- 平台超管
  - 管租户开通、停用、全局告警、全局审计
- 租户管理员
  - 对应系统角色 `TenantAdmin`
  - 管本租户员工、项目、账户接入配置、账号授权、任务查看
- 优化师
  - 对应系统角色 `Optimizer`
  - 发起扫码获取执行凭证、提交任务、执行被授权广告账户的操作

MVP 当前不再拆分设计师、只读人员、项目管理员等额外角色，避免权限模型过早复杂化。
后续如业务确实需要，再从租户管理员或优化师能力中拆分独立角色。

### 4.7 MVP 权限原则
MVP 阶段，权限分两层即可：

- 功能权限：能不能配置账户接入、建项目、加员工、发任务、看日志
- 数据权限：能看哪些项目、哪些投放账号、哪些任务

其中，功能权限直接复用 `MineAdmin` 菜单/按钮权限，数据权限通过 `tenant_id + project_id + account authorization` 控制。

MVP 不做过细的权限引擎，先按以下规则落地：

- 平台账号不受租户/项目作用域限制
- 租户账号默认先按 `tenant_id` 隔离
- 带 `project_id` 的业务数据再按当前项目隔离
- 租户管理员可看本租户全部项目、全部成员、全部账号
- 优化师只能看自己加入的项目，以及被授权的投放账号
- 素材、模板、任务、日志都默认跟项目权限走

MVP 的执行权限链明确为：

```text
先加入项目
-> 再授权广告主账号
-> 再获取或使用可用 userToken
-> 才能执行任务
```

也就是说：

- 项目权限解决“能不能进入项目”
- 广告主账号授权解决“能操作哪几个广告主账户”
- 可用 `userToken` 解决“本次任务是否可真正执行”

需要注意，“授权”在产品上不是一个单独菜单，而是两个动作：

- 在 `团队项目管理` 中配置项目成员，解决项目授权
- 在 `投放账号管理 -> 广告主账号` 中分配广告主账号，解决账号授权

### 4.8 员工、项目、账号关系
```text
租户
├── 员工
├── 项目
│   ├── 选择并授权广告主账号
│   └── 产出任务/模板/素材
└── 员工加入项目
    └── 员工再获得广告主账户授权
```

MVP 约束如下：

- 一个租户下可有多个项目
- 租户至少需要被平台分配一个可用腾讯第三方应用，才能授权广告主账号
- 新租户自动生成一个“主项目”
- 一个员工可加入多个项目
- 广告主账号在产品上直接授权并导入，系统内部仍保留授权来源记录
- 广告主账号归属到项目
- 一个员工只有加入项目后，才可以被授权该项目下的广告主账户
- 广告投放类任务必须归属一个项目
- 平台级、租户级导出任务可不挂项目，但也统一进入任务中心

### 4.9 素材、模板与任务归属
MVP 阶段，素材、模板继续按项目归属和项目权限控制；任务中心则统一承接广告任务与导出任务，不做“每个页面一套导出实现”。

也就是说：

- 素材跟项目权限走
- 模板跟项目权限走
- 广告投放任务跟项目权限走
- 所有导出统一进入任务中心
- 导出任务按 `platform / tenant / project` 作用域控制可见范围

这样做的好处是：

- 权限判断最简单
- 审计最清楚
- 和竞品的项目协作方式一致
- 导出入口统一，后续扩展报表导出、任务日志导出、账号数据导出都不用重复造轮子
- 后续要扩展“租户素材库”时，也不会推翻现有结构

### 4.10 平台应用与广告主账号
MVP 阶段，这两层关系要明确区分：

- 平台应用：由平台统一管理并分配给租户使用的腾讯第三方应用
- 授权来源记录：系统内部保存的 OAuth 授权身份与同步来源，不单独作为产品菜单暴露
- 广告主账号：真正执行广告投放的账户

产品上的主链路应为：

```text
平台管理应用
-> 平台分配应用给租户
-> 租户在广告主账号中直接发起授权
-> 系统内部记录授权来源
-> 选择并导入广告主账号
-> 广告主账号归属项目
-> 在团队项目管理中配置项目成员
-> 在广告主账号中授权给员工
-> 扫码获取执行凭证后执行
```

这也是为什么应用能力虽然是业务前置条件，但在租户侧 MVP 阶段不单独挂菜单，而是收敛到 `投放账号管理` 的授权流程中；租户只使用平台已分配应用，不自行维护应用配置；OAuth 授权来源只作为后台记录，不单独要求用户理解和维护。

### 4.11 广告主账户与项目关系
MVP 虽然只做腾讯广告，但业务上需要明确：

- 广告主账户：真正用于投放和任务执行的账户
- 项目：广告主账户、员工授权、任务、素材、模板的统一归属边界

可简单理解为：

```text
项目
-> 广告主账户
-> 员工账号授权
```

后续如果腾讯侧接入方式发生变化，再补充中间接入层也不迟；MVP 先以最短链路跑通业务闭环。

### 4.12 执行身份
MVP 虽然简化了组织层级，但执行身份不能省。

一次任务至少要记录：

- 任务发起人
- 执行凭证所属员工
- 凭证获取会话
- 执行凭证记录

也就是说：

- 腾讯扫码回调当前只用于给某个本地员工绑定一份可用 `userToken`
- 如回调中返回微信昵称，也只用于展示和审计，不作为权限依据
- “谁提交了任务”不等于“谁提供了本次执行所用的 userToken”
- “谁能看任务”不等于“谁有权执行广告接口”

## 5. MVP 范围
一期只做以下内容：

- 平台管理租户
- 平台管理应用并分配给租户
- 租户管理项目
- 租户管理员工
- 项目管理广告主账户
- 员工项目授权与广告主账户授权
- 员工扫码获取 `userToken` 与执行凭证管理
- 批量建广告主任务/子任务
- 各业务导出统一进入任务中心
- 异步任务执行与重试
- 基础通知与基础审计

## 6. 结论
本项目最快落地、又方便扩展的组织架构，不是“只做租户”，也不是“一上来做复杂组织树”，而是：

```text
平台 -> 租户 -> 项目 -> 广告主账户 -> 员工授权 -> 任务
```

MVP 先把这几层做稳定：

- 平台负责管理租户与应用分配
- 租户负责管理项目与员工
- 项目负责承接广告主账户、模板、素材、任务
- 员工先获得项目权限，再获得广告主账户授权，最后通过可用执行凭证执行任务

这套结构足够简单，能最快落地，也能承接后续扩展。
