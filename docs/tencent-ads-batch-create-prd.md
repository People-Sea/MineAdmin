# 风起（批量广告投放系统）PRD（腾讯广告 MVP 版）

## 1. 背景
当前项目“风起（批量广告投放系统）”准备接入腾讯广告，为多个客户提供批量创建广告的能力。

该场景与普通后台系统不同，主要有 4 个现实约束：

- 系统服务多个客户，必须具备多租户隔离能力。
- 每个客户必须使用自己的腾讯广告第三方应用，不能共用平台统一应用。
- 广告执行不能长期依赖固定凭证，必须由员工扫码获取临时执行凭证。
- 广告创建、更新、重试都是长链路操作，必须走异步任务。

从业务风险上看，如果某个员工的执行凭证异常或被封，不能影响其他员工、其他项目、其他租户。

因此，本产品的 MVP 目标不是做一个“大而全”的多租户平台，而是先做出一套最小可跑通的闭环：

- 平台能管理多个租户
- 租户能管理员工与项目
- 项目能管理腾讯接入主体、广告主账户、素材与任务
- 员工能扫码获取执行凭证
- 系统能异步执行批量建广告任务

## 2. 解决方案（技术选型）
### 2.1 后端框架
- 使用现有 `MineAdmin` 作为后台基础框架。
- `MineAdmin` 底层依赖 `Hyperf`，继续承担平台后台能力，不再引入官方多租户插件。

### 2.2 数据存储
- 使用 `MySQL` 存储租户、项目、员工、任务、日志等业务数据。
- 使用 `Redis` 承担缓存、队列、临时状态存储。

### 2.3 异步任务
- 使用 `hyperf/async-queue` 作为广告创建、更新、重试的主执行链路。
- 使用 `hyperf/crontab` 做超时巡检、补偿、通知补发，不承担主执行流程。

### 2.4 腾讯广告接入
- 使用腾讯广告官方 API / OAuth 能力对接应用授权、账户授权和广告接口调用。
- 本文中的 `userToken` 先作为业务命名，表示“员工扫码后获得的临时执行凭证”。
- 后续开发时，需要在接口对接阶段进一步确认 `userToken` 与腾讯官方 OAuth 字段的对应关系。
- MVP 当前只做腾讯广告，不额外抽象多媒体统一层。
- 但在数据模型上，仍区分“腾讯接入主体”和“广告主账户”两个对象，避免后续混淆。

### 2.5 安全策略
- 应用密钥、执行凭证加密存储。
- 队列消息体只传业务 ID，不传明文敏感凭证。
- 所有任务执行链路必须可审计、可追踪。

## 3. 框架架构
MVP 阶段采用“平台域 + 租户业务域 + 腾讯接入域 + 异步任务域”四层结构。

### 3.1 总体结构
```text
+----------------------+
| 平台后台基础框架      |
| MineAdmin            |
| 租户开通/审计/告警    |
+----------+-----------+
           |
           v
+----------------------+
| 租户业务域            |
| 租户/项目/员工/权限链 |
| 模板/素材/任务        |
+----------+-----------+
           |
           +------------------+
           |                  |
           v                  v
+------------------+   +--------------------+
| 腾讯广告接入域    |   | 异步任务域          |
| 接入主体/广告主号 |   | async-queue/crontab|
+------------------+   +--------------------+
```

### 3.2 平台域
平台域继续使用现有 `MineAdmin` 账号体系，只服务“风起（批量广告投放系统）”的平台运营人员。

平台域只负责：

- 租户开通、停用
- 平台级审计
- 全局异常排查
- 平台告警

平台域不直接承担租户员工体系，不与租户员工共用角色模型。

### 3.3 租户业务域
租户业务域采用独立建模，负责：

- 租户
- 项目
- 员工
- 项目成员
- 项目权限
- 腾讯接入主体
- 广告主账户
- 广告主账户授权
- 认证会话与执行凭证
- 广告素材、模板、任务与任务日志

### 3.4 腾讯接入域
负责：

- 腾讯广告应用配置校验
- 广告账户授权回收
- 广告接口调用
- 凭证刷新与异常识别

### 3.5 异步任务域
负责：

- 主任务/子任务拆分
- 执行状态流转
- 失败重试
- 补偿与通知

## 4. 产品组织架构
MVP 阶段，产品组织架构尽量简单，只保留 4 层：

- 平台
- 租户
- 项目
- 员工

其中，租户仍需要有“租户自己的腾讯第三方应用配置”这一层基础能力，但 MVP 不单独做 `应用管理` 菜单，而是先收敛到 `投放账号管理 -> 管家账号绑定流程` 中；“管家账号”“广告主账号”“模板”“素材”“任务”则围绕项目展开。租户是管理边界，项目是用户日常操作的主工作上下文。

### 4.1 组织关系图
```text
平台
└── 租户
    ├── 主项目（默认生成）
    ├── 项目 A
    │   ├── 管家账号
    │   ├── 广告主账号
    │   ├── 模板
    │   ├── 素材
    │   └── 任务
    ├── 项目 B
    └── 员工
        ├── 企业管理员
        ├── 操作员
        ├── 设计师
        └── 只读人员
```

### 4.2 项目是主工作上下文
在“风起（批量广告投放系统）”里，项目不是一个普通字段，也不是一个附属筛选项，而是租户侧业务操作的主视角。

员工登录后，除少数租户管理页外，默认都应在某个项目上下文中工作。

也就是说，项目切换后，以下内容都应随之切换：

- 管家账号
- 广告主账号
- 素材
- 模板
- 任务
- 报表
- 账号授权结果

MVP 阶段建议产品交互遵循以下原则：

- 员工登录后，优先进入自己最近使用或默认可进入的项目
- 页面顶部提供全局“当前项目”切换能力
- 除企业管理员外，普通员工只能切换自己已加入的项目
- 除租户管理页外，业务页面默认基于当前项目展示数据

### 4.3 MVP 后台菜单结构
MVP 阶段，租户后台建议直接对齐竞品的使用习惯，围绕“配置管理 + 业务模块”来组织，而不是暴露过多技术概念。

建议一级菜单如下：

- 工作台
- 配置管理
- 素材中心
- 模板中心
- 任务中心
- 报表与日志

其中，`配置管理` 下的核心模块建议如下：

- 团队人员管理
- 团队项目管理
- 投放账号管理
  - 管家账号
  - 广告主账号

这里有两个产品原则：

- 租户自己的腾讯第三方应用配置是租户级能力，但 MVP 不单独挂 `应用管理` 菜单，先放进 `管家账号` 绑定流程
- `投放账号管理` 是项目工作流里的资源管理入口，其中 `管家账号` 是上层接入入口，`广告主账号` 是真实投放对象

### 4.4 产品口径与技术口径
为了贴近用户理解，产品页面建议直接使用竞品同类口径：

- 产品页叫 `管家账号`
- 产品页叫 `广告主账号`
- 产品页叫 `团队项目管理`
- 产品页叫 `团队人员管理`
- 产品页叫 `投放账号管理`

但在技术实现中，可以继续使用更稳定的内部抽象：

- `管家账号` 对应内部的“腾讯接入主体”
- `广告主账号` 对应内部的“广告主账户”

这样做的目的，是让前台交互更贴近行业常用说法，同时避免把腾讯某个阶段性的旧名词直接写死进底层模型。

### 4.5 为什么 MVP 要保留“项目”
项目是本产品最快落地、同时最方便扩展的中间层。

不加项目会带来两个问题：

- 接入主体、广告主账户、模板、素材、任务都会直接堆在租户下，后续难管理。
- 员工的数据权限只能在“全租户”级别做控制，粒度过粗。

MVP 先引入项目，可以同时解决：

- 管家账号与广告主账号分组管理
- 员工按项目协作
- 任务归属清晰
- 后续报表按项目聚合更自然

### 4.6 MVP 角色模型
MVP 只保留最少角色，不做复杂角色树。

- 平台超管
  - 管租户开通、停用、全局告警、全局审计
- 企业管理员
  - 管本租户员工、项目、账户接入配置、账号授权、任务查看
- 操作员
  - 发起扫码、提交任务、执行被授权广告账户的操作
- 设计师
  - 管理素材与创意，不直接操作广告账户
- 只读人员
  - 查看结果、报表、日志

为避免 MVP 复杂化，暂不单独引入“项目管理员”角色。
如后续需要，可以从“企业管理员”拆出“项目管理员”。

### 4.7 MVP 权限原则
MVP 阶段，权限分两层即可：

- 功能权限：能不能配置账户接入、建项目、加员工、发任务、看日志
- 数据权限：能看哪些项目、哪些投放账号、哪些任务

MVP 不做过细的权限引擎，先按以下规则落地：

- 企业管理员可看本租户全部项目与全部账号
- 操作员只能看自己加入的项目，以及被授权的投放账号
- 设计师只能看自己加入项目下的素材数据
- 只读人员只能看自己加入项目下的结果数据

MVP 的执行权限链明确为：

```text
先加入项目
-> 再授权广告主账号
-> 再完成扫码认证
-> 才能执行任务
```

也就是说：

- 项目权限解决“能不能进入项目”
- 广告主账号授权解决“能操作哪几个广告主账户”
- 扫码认证解决“本次任务是否可真正执行”

需要注意，“授权”在产品上不是一个单独菜单，而是两个动作：

- 在 `团队项目管理` 中配置项目成员，解决项目授权
- 在 `投放账号管理 -> 广告主账号` 中分配广告主账号，解决账号授权

### 4.8 员工、项目、账号关系
```text
租户
├── 员工
├── 项目
│   ├── 绑定管家账号
│   ├── 选择广告主账号
│   └── 产出任务/模板/素材
└── 员工加入项目
    └── 员工再获得广告主账户授权
```

MVP 约束如下：

- 一个租户下可有多个项目
- 一个租户至少配置一个腾讯第三方应用
- 新租户自动生成一个“主项目”
- 一个员工可加入多个项目
- 一个管家账号属于一个项目
- 广告主账号由管家账号同步或管理，并归属到项目
- 一个员工只有加入项目后，才可以被授权该项目下的广告主账户
- 一个任务必须归属一个项目

### 4.9 素材、模板与任务归属
MVP 阶段，素材、模板、任务均按项目归属和项目权限控制，不做整个租户内默认共享。

也就是说：

- 素材跟项目权限走
- 模板跟项目权限走
- 任务跟项目权限走

这样做的好处是：

- 权限判断最简单
- 审计最清楚
- 和竞品的项目协作方式一致
- 后续要扩展“租户素材库”时，也不会推翻现有结构

### 4.10 应用、管家账号与广告主账号
MVP 阶段，这三层关系要明确区分：

- 租户应用配置：租户自己的腾讯第三方应用配置
- 管家账号：用于承接腾讯侧接入、同步账户、发起授权的上层账号入口
- 广告主账号：真正执行广告投放的账户

产品上的主链路应为：

```text
在管家账号绑定流程中配置租户应用
-> 绑定管家账号
-> 选择广告主账号并归属项目
-> 在团队项目管理中配置项目成员
-> 在广告主账号中授权给员工
-> 扫码执行
```

这也是为什么“租户应用配置”虽然属于租户级能力，但在 MVP 阶段不单独挂菜单，而是收敛到 `投放账号管理` 的接入流程中。

### 4.11 腾讯接入主体与广告主账户
MVP 虽然只做腾讯广告，但业务上仍需区分：

- 腾讯接入主体：承接授权方式、接入配置、同步账户等能力
- 广告主账户：真正用于投放和任务执行的账户

可简单理解为：

```text
项目
-> 腾讯接入主体
-> 广告主账户
-> 员工账号授权
```

### 4.12 执行身份
MVP 虽然简化了组织层级，但执行身份不能省。

一次任务至少要记录：

- 任务发起人
- 认证执行人
- 认证会话
- 执行凭证版本

也就是说：

- “谁提交了任务”不等于“谁扫码执行了任务”
- “谁能看任务”不等于“谁有权执行广告接口”

## 5. MVP 范围
一期只做以下内容：

- 平台管理租户
- 租户管理项目
- 租户管理员工
- 项目绑定腾讯接入主体
- 项目管理广告主账户
- 员工项目授权与广告主账户授权
- 员工扫码认证与执行凭证管理
- 批量建广告主任务/子任务
- 异步任务执行与重试
- 基础通知与基础审计

## 6. 结论
本项目最快落地、又方便扩展的组织架构，不是“只做租户”，也不是“一上来做复杂组织树”，而是：

```text
平台 -> 租户 -> 项目 -> 腾讯接入主体/广告主账户 -> 员工授权 -> 任务
```

MVP 先把这几层做稳定：

- 平台负责管理租户
- 租户负责管理项目与员工
- 项目负责承接腾讯接入主体、广告主账户、模板、素材、任务
- 员工先获得项目权限，再获得广告主账户授权，最后通过扫码执行任务

这套结构足够简单，能最快落地，也能承接后续扩展。
