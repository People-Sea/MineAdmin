# 风起（批量广告投放系统）PRD（腾讯广告存量资产 MVP 版）

## 1. 背景
当前项目“风起（批量广告投放系统）”准备接入腾讯广告。

当前一期 MVP 先聚焦“腾讯广告存量资产拉取 / 编辑 / 复审”闭环，批量创建广告与统一任务中心能力放到二期推进。

该场景与普通后台系统不同，主要有 4 个现实约束：

- 系统服务多个客户，必须具备多租户隔离能力。
- 租户授权广告主账号时，必须使用平台分配的腾讯广告第三方应用，不再由租户自行配置应用。
- 广告执行不能长期依赖固定凭证，必须由员工获取临时执行凭证。
- 广告数据同步、审核结果回查和后续批量创建都属于长链路操作，当前需要预留异步任务扩展位。

从业务风险上看，如果某个员工的执行凭证异常或被封，不能影响其他员工、其他项目、其他租户。

因此，本产品的一期 MVP 目标不是做一个“大而全”的多租户平台，也不是直接进入批量创建链路，而是先做出一套最小可跑通的闭环：

- 平台能管理多个租户
- 租户能管理员工与项目
- 项目能管理广告主账户与员工授权
- 员工能获取执行凭证
- 系统能拉取广告数据、同步审核状态并完成未通过项复审

## 2. 解决方案（技术选型）
### 2.1 后端框架
- 使用现有 `MineAdmin` 作为后台基础框架。
- `MineAdmin` 底层依赖 `Hyperf`，继续承担平台后台能力，不再引入官方多租户插件。

### 2.2 数据存储
- 使用 `MySQL` 存储租户、项目、员工、任务、日志等业务数据。
- 使用 `Redis` 承担缓存、队列、临时状态存储。

### 2.3 异步任务与调度
- 一期 MVP 先不建设统一 `hyperf/async-queue` 主执行链路，页面主流程以同步调用为主。
- 一期使用 `hyperf/crontab` 做状态同步、超时巡检、补偿与通知补发。
- 二期再接入 `hyperf/async-queue`，承接批量创建、失败重试和统一任务中心。

### 2.4 腾讯广告接入
- 使用腾讯广告官方 API / OAuth 能力对接应用授权、账户授权和广告接口调用。
- 接口资料以腾讯广告官方开发者门户 `developers.e.qq.com/v3.0` 为主入口；具体请求版本以对应接口页面当前声明为准。
- 租户授权广告主账号的链路，按官方当前文档应理解为：`oauth/authorize -> oauth/token 或 oauth/refresh_token -> advertiser/get`。
- OAuth 回调核心结果是 `authorization_code` 与 `state`；`authorization_code` 只用于换取 `access_token / refresh_token`，不应与执行身份凭证混用。
- 官方受限接口中的执行身份参数名是 `user_token`，页面说明为“实名认证完成获取的令牌”，且明确要求作为请求参数传递，不放在 header 中。
- 当前阶段，`user_token` 只用于给本地员工提供受限接口执行身份，不承担本地账号识别和权限判断。
- `user_token` 的有效期与获取方式以腾讯当前“API 身份验证升级公告”及开发者对接文档为准，项目文档中不再写死 15 天。
- MVP 当前只做腾讯广告，不额外抽象多媒体统一层。
- 产品层直接围绕“广告主账户”做授权和投放，不单独暴露“管家账号 / 授权主体”菜单。
- 技术层保留一层“授权来源记录”，用于保存 OAuth 授权身份、token 刷新和账号同步来源。
- 腾讯广告第三方应用由平台统一管理，并分配给租户使用；租户在授权广告主账号时，必须使用平台已分配应用。

### 2.5 安全策略
- 应用密钥、执行凭证加密存储。
- 队列消息体只传业务 ID，不传明文敏感凭证。
- 所有任务执行链路必须可审计、可追踪。

## 3. 框架架构
整体架构仍采用“平台域 + 租户业务域 + 腾讯接入域 + 异步任务域”四层结构。
当前一期 MVP 主线聚焦平台域、租户业务域和腾讯接入域；异步任务域只保留扩展边界，放在二期落地。

### 3.1 总体结构
```text
+----------------------+
| 平台后台基础框架      |
| MineAdmin            |
| 租户开通/审计/告警    |
+----------+-----------+
           |
           v
+----------------------+
| 租户业务域            |
| 租户/项目/员工/权限链 |
| 广告/创意/组件/审核   |
+----------+-----------+
           |
           +------------------+
           |                  |
           v                  v
+------------------+   +--------------------+
| 腾讯广告接入域    |   | 异步任务域          |
| 广告主账号接入/授权 | | async-queue/crontab|
+------------------+   +--------------------+
```

### 3.2 平台域
平台域继续使用现有 `MineAdmin` 账号体系，只服务“风起（批量广告投放系统）”的平台运营人员。

平台域只负责：

- 租户开通、停用
- 平台应用管理与分配
- 平台级审计
- 全局异常排查
- 平台告警

平台域与租户域共用同一套 `MineAdmin user / role / menu` 体系。
MVP 阶段不再单独建设 `tenant_member` 认证链，而是在统一 `user` 模型上补充 `tenant_id`、`last_project_id` 等字段，再用项目成员关系与账号授权关系完成数据隔离。

### 3.3 租户业务域
租户业务域负责：

- 租户
- 项目
- 租户员工与项目成员关系
- 项目权限
- 广告主账户授权来源记录
- 广告主账户
- 广告主账户授权
- 凭证获取会话与执行凭证
- 广告数据、创意数据、创意组件数据
- 审核结果同步、元素申诉复审与催审记录

### 3.4 腾讯接入域
负责：

- 平台分配应用校验
- 广告主账户授权回收
- 广告接口调用
- 凭证刷新与异常识别

### 3.5 异步任务域
二期负责：

- 主任务/子任务拆分
- 执行状态流转
- 失败重试
- 补偿与通知

## 4. 产品组织架构
MVP 阶段，产品组织架构尽量简单，只保留 4 层：

- 平台
- 租户
- 项目
- 员工

其中，腾讯广告第三方应用由平台统一管理并分配给租户使用；租户侧不单独做 `应用管理` 菜单，也不单独暴露“授权主体 / 管家账号”菜单，而是在 `投放账号管理 -> 广告主账号` 中直接完成授权与选择；当前 MVP 的“广告”“创意”“创意组件”“审核结果”都围绕项目展开。租户是管理边界，项目是用户日常操作的主工作上下文。

### 4.1 组织关系图
```text
平台
├── 应用
└── 租户
    ├── 主项目（默认生成）
    ├── 项目 A
    │   ├── 广告主账号
    │   ├── 广告
    │   ├── 创意
    │   ├── 创意组件
    │   └── 审核结果
    ├── 项目 B
    └── 员工
        ├── 租户管理员
        └── 优化师
```

### 4.2 项目是主工作上下文
在“风起（批量广告投放系统）”里，项目不是一个普通字段，也不是一个附属筛选项，而是租户侧业务操作的主视角。

员工登录后，除少数租户管理页外，默认都应在某个项目上下文中工作。

也就是说，项目切换后，以下内容都应随之切换：

- 广告主账号
- 广告
- 创意
- 创意组件
- 审核结果
- 账号授权结果

MVP 阶段建议产品交互遵循以下原则：

- 平台用户与租户用户统一使用 `/login`
- 不再保留 `/tenant/login` 兼容入口，统一收敛到 `/login`
- 平台用户与租户用户共用同一套 `username + password` 登录凭证模型
- 统一登录入口下，`username` 采用全局唯一规则，不按租户内重复创建
- 租户用户通过 `user.tenant_id` 识别所属租户，不再额外引入邮箱登录链
- 员工登录后，优先进入自己最近使用或默认可进入的项目
- 页面顶部提供全局“当前项目”切换能力
- 租户管理员可切换本租户全部项目，优化师只能切换自己已加入的项目
- 除租户管理页外，业务页面默认基于当前项目展示数据

### 4.3 MVP 后台菜单结构
MVP 阶段，租户后台建议直接对齐竞品的使用习惯，围绕“配置管理 + 业务模块”来组织，而不是暴露过多技术概念。

建议一级菜单如下：

- 工作台
- 配置管理
- 广告管理
- 审核与日志
- 报表与日志

其中，`配置管理` 下的核心模块建议如下：

- 团队人员管理
- 团队项目管理
- 投放账号管理
  - 广告主账号

这里有两个产品原则：

- 腾讯第三方应用由平台统一管理并分配给租户；租户侧不单独挂 `应用管理` 菜单，授权时直接使用已分配应用
- 租户侧不单独暴露“管家账号 / 授权主体”概念；用户在 `广告主账号` 中直接发起授权、选择并导入广告主账号
- `团队项目管理` 只负责项目与成员配置；广告主账号的授权、导入和归属在 `投放账号管理` 中完成
- `投放账号管理` 是项目工作流里的资源管理入口，`广告主账号` 是真实投放对象，也是当前 MVP 唯一需要暴露的投放账号模型

### 4.4 产品口径与技术口径
为了贴近用户理解，产品页面建议直接使用竞品同类口径：

- 产品页叫 `广告主账号`
- 产品页叫 `团队项目管理`
- 产品页叫 `团队人员管理`
- 产品页叫 `投放账号管理`

在技术实现中，也保持简单直接：

- `广告主账号` 对应内部的“广告主账户”
- 应用配置由平台管理；租户侧只感知“当前已分配可用应用”，不直接维护应用密钥
- 租户侧页面不单独出现“授权主体”菜单，但系统内部保留 OAuth 授权来源记录

这样做的目的，是让前台交互和底层模型尽量一致，避免为了未来不确定场景过早引入中间层。

### 4.5 为什么 MVP 要保留“项目”
项目是本产品最快落地、同时最方便扩展的中间层。

不加项目会带来两个问题：

- 广告主账户、广告、创意、创意组件、审核结果都会直接堆在租户下，后续难管理。
- 员工的数据权限只能在“全租户”级别做控制，粒度过粗。

MVP 先引入项目，可以同时解决：

- 广告主账号分组管理
- 员工按项目协作
- 任务归属清晰
- 后续报表按项目聚合更自然

### 4.6 MVP 角色模型
MVP 只保留最少角色，不做复杂角色树。

- 角色能力直接复用 `MineAdmin` 角色与菜单权限体系，不再维护一套平行角色枚举
- 平台超管
  - 管租户开通、停用、全局告警、全局审计
- 租户管理员
  - 对应系统角色 `TenantAdmin`
  - 管本租户员工、项目、账户接入配置、账号授权、任务查看
- 优化师
  - 对应系统角色 `Optimizer`
  - 发起执行凭证获取、提交任务、执行被授权广告账户的操作

MVP 当前不再拆分设计师、只读人员、项目管理员等额外角色，避免权限模型过早复杂化。
后续如业务确实需要，再从租户管理员或优化师能力中拆分独立角色。

### 4.7 MVP 权限原则
MVP 阶段，权限分两层即可：

- 功能权限：能不能配置账户接入、建项目、加员工、拉取数据、编辑复审、看日志
- 数据权限：能看哪些项目、哪些投放账号、哪些广告/创意/组件/审核记录

其中，功能权限直接复用 `MineAdmin` 菜单/按钮权限，数据权限通过 `tenant_id + project_id + account authorization` 控制。

MVP 不做过细的权限引擎，先按以下规则落地：

- 平台账号不受租户/项目作用域限制
- 租户账号默认先按 `tenant_id` 隔离
- 带 `project_id` 的业务数据再按当前项目隔离
- 租户管理员可看本租户全部项目、全部成员、全部账号
- 优化师只能看自己加入的项目，以及被授权的投放账号
- 广告、创意、创意组件、审核记录都默认跟项目权限走

MVP 的执行权限链明确为：

```text
先加入项目
-> 再授权广告主账号
-> 再获取或使用可用 user_token
-> 才能执行任务
```

也就是说：

- 项目权限解决“能不能进入项目”
- 广告主账号授权解决“能操作哪几个广告主账户”
- 可用 `user_token` 解决“本次任务是否可真正执行”

需要注意，“授权”在产品上不是一个单独菜单，而是两个动作：

- 在 `团队项目管理` 中配置项目成员，解决项目授权
- 在 `投放账号管理 -> 广告主账号` 中分配广告主账号，解决账号授权

### 4.8 员工、项目、账号关系
```text
租户
├── 员工
├── 项目
│   ├── 选择并授权广告主账号
│   └── 拉取广告/创意/创意组件并执行复审
└── 员工加入项目
    └── 员工再获得广告主账户授权
```

MVP 约束如下：

- 一个租户下可有多个项目
- 租户至少需要被平台分配一个可用腾讯第三方应用，才能授权广告主账号
- 新租户自动生成一个“主项目”
- 一个员工可加入多个项目
- 广告主账号在产品上直接授权并导入，系统内部仍保留授权来源记录
- 广告主账号归属到项目
- 一个员工只有加入项目后，才可以被授权该项目下的广告主账户
- 当前拉取、编辑、复审操作必须归属一个项目
- 二期异步任务与导出任务再进入统一任务中心

### 4.9 广告、创意、组件与审核归属
当前 MVP 阶段，广告、创意、创意组件和审核结果都按项目归属和项目权限控制。

也就是说：

- 广告跟项目权限走
- 创意跟项目权限走
- 创意组件跟项目权限走
- 审核结果跟项目权限走
- 二期再把异步任务和导出统一收敛到任务中心

这样做的好处是：

- 权限判断最简单
- 审计最清楚
- 和竞品的项目协作方式一致
- 后续接入批量创建和任务中心时，不会推翻现有项目边界

### 4.10 平台应用与广告主账号
MVP 阶段，这两层关系要明确区分：

- 平台应用：由平台统一管理并分配给租户使用的腾讯第三方应用
- 授权来源记录：系统内部保存的 OAuth 授权身份与同步来源，不单独作为产品菜单暴露
- 广告主账号：真正执行广告投放的账户

产品上的主链路应为：

```text
平台管理应用
-> 平台分配应用给租户
-> 租户在广告主账号中直接发起授权
-> OAuth 回调拿到 authorization_code
-> 系统内部记录授权来源并换取 access_token / refresh_token
-> 使用 `advertiser/get` 为主、必要时结合 `organization_account_relation/get` 拉取广告主账号
-> 选择并导入广告主账号
-> 广告主账号归属项目
-> 在团队项目管理中配置项目成员
-> 在广告主账号中授权给员工
-> 员工获取可用 `user_token` 后执行
```

这也是为什么应用能力虽然是业务前置条件，但在租户侧 MVP 阶段不单独挂菜单，而是收敛到 `投放账号管理` 的授权流程中；租户只使用平台已分配应用，不自行维护应用配置；OAuth 授权来源只作为后台记录，不单独要求用户理解和维护。

### 4.11 广告主账户与项目关系
MVP 虽然只做腾讯广告，但业务上需要明确：

- 广告主账户：真正用于投放和任务执行的账户
- 项目：广告主账户、员工授权、广告数据、创意数据、创意组件数据、审核结果的统一归属边界

可简单理解为：

```text
项目
-> 广告主账户
-> 员工账号授权
```

后续如果腾讯侧接入方式发生变化，再补充中间接入层也不迟；MVP 先以最短链路跑通业务闭环。

### 4.12 执行身份
MVP 虽然简化了组织层级，但执行身份不能省。

一次任务至少要记录：

- 任务发起人
- 执行凭证所属员工
- 凭证获取会话
- 执行凭证记录

也就是说：

- 腾讯实名链路当前只用于给某个本地员工绑定一份可用 `user_token`
- 如回调中返回微信昵称，也只用于展示和审计，不作为权限依据
- “谁提交了任务”不等于“谁提供了本次执行所用的 user_token”
- “谁能看任务”不等于“谁有权执行广告接口”

### 4.13 当前 MVP 的最快闭环
当前一期 MVP 的最小可交付不做“批量创建广告”主链路，优先做“拉取 + 编辑 + 复审”闭环：

- 拉取广告数据（含审核状态）
- 拉取广告创意数据（含审核状态）
- 拉取创意组件数据（含审核状态）
- 支持对未通过项进行编辑
- 支持再次提交审核并回查审核结果

这样做的目标是先解决“账户下现有资产的持续可运营”，把账号可用性和复审效率先跑通，再进入批量创建广告能力。

## 5. MVP 范围
一期 MVP 只做“腾讯广告存量资产拉取 / 编辑 / 复审”闭环，范围包括：

- 平台管理租户
- 平台管理应用并分配给租户
- 租户管理项目
- 租户管理员工
- 项目管理广告主账户
- 员工项目授权与广告主账户授权
- 员工获取 `user_token` 实名执行凭证与执行身份管理
- 拉取广告、创意、创意组件及其审核状态
- 支持未通过项编辑并再次提交审核
- 审核结果回查与状态同步
- 基础通知与基础审计

### 5.1 二期范围（保留）
二期继续推进异步任务与批量创建能力，范围包括：

- 批量建广告主任务/子任务
- 统一任务中心与导出任务收敛
- `hyperf/async-queue` 执行链路
- 失败重试、补偿和告警

## 6. 结论
本项目最快落地、又方便扩展的组织架构，不是“只做租户”，也不是“一上来做复杂组织树”，而是：

```text
平台 -> 租户 -> 项目 -> 广告主账户 -> 员工授权 -> user_token 执行凭证
```

MVP 先把这几层做稳定：

- 平台负责管理租户与应用分配
- 租户负责管理项目与员工
- 项目负责承接广告主账户与成员协作边界
- 员工先获得项目权限，再获得广告主账户授权，最后通过可用执行凭证进行拉取、编辑与复审操作

这套结构足够简单，能最快落地，也能承接后续扩展。
